# Contributing to ratchet4j

Thanks for helping! This project is small and the codebase is easy to get into. Bug reports from
real projects are as valuable as code.

## The most useful thing you can do

Run ratchet4j on a real project, change some code (add lines, reformat, move a method, rename a
file) and see whether old violations are wrongly reported as **new**. If they are, open an issue
with the smallest report excerpt and source snippet that shows it. A wrongly "new" violation is
the worst bug this tool can have, because it blocks developers and destroys trust.

## Development setup

You need JDK 17 or newer and Maven 3.9+.

```bash
git clone https://github.com/ratchet4j/ratchet4j.git
cd ratchet4j
mvn verify          # compile + all tests
```

The runnable jar is built at `ratchet-cli/target/ratchet.jar`.

## Project layout

| Module | Contents |
|---|---|
| `ratchet-core` | model, normalizer, fingerprinter, matcher, policy, baseline IO, ratchet, `Engine` |
| `ratchet-readers` | report readers (SARIF, Checkstyle, PMD, SpotBugs) and format detection |
| `ratchet-cli` | the `ratchet` command line |

Read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) first; it explains the fingerprint and matching design.

## What CI checks

Every pull request must pass the single check **CI OK**, which is green only if all of these pass:

- build and tests on Java 17 and 21 (Linux) and on Windows and macOS
- a smoke test of the packaged jar
- the **self-check**: ratchet4j runs Checkstyle (Google style) on its own code and fails on **new**
  violations. The ones that existed on day one are recorded in `ratchet-baseline.json`
- Markdown link check and workflow lint (actionlint)

### The self-check

If you add a Google-style violation (for example a line longer than 100 characters), CI fails and
prints the file and line. Fix it. When you *fix* old violations, shrink the baseline so the progress
is locked in:

```bash
mvn -DskipTests package
java -jar checkstyle.jar -c /google_checks.xml -f xml -o target/self-checkstyle.xml \
  ratchet-core/src ratchet-readers/src ratchet-cli/src
java -jar ratchet-cli/target/ratchet.jar update --root . --input target/self-checkstyle.xml
```

(`checkstyle.jar` is Checkstyle 10.17.0 "all" jar; see `.github/workflows/ci.yml` for the exact
download.) Never grow the baseline to make CI pass.

## Releases

Releases happen every second month and are automated; see [docs/RELEASING.md](docs/RELEASING.md).

## Ground rules

1. **No runtime dependencies** in `ratchet-core` and `ratchet-readers`. If you think one is needed,
   open an issue first and explain why the JDK is not enough.
2. **Determinism.** The same input must produce byte-identical output, in any input order, on any OS.
   No timestamps, no locale-dependent formatting, no hash-map iteration order leaking into output.
3. **Tests come first for the matcher.** Any change to fingerprinting or matching starts with a new
   scenario in `RefactoringScenariosTest` that fails, then the fix. Describe the real-world edit the
   scenario models.
4. **Real data for readers.** Reader tests should use reports generated by the real tool. Say in the
   test or fixture README which tool, version and command produced the file.
5. **Prefer a missed violation to a false "new" one**, but never match one baseline entry twice.
6. Keep changes focused: one pull request, one purpose.

## Adding support for another analyzer

1. Implement `ViolationReader` in `ratchet-readers` (`name()`, `supports(head)`, `read(...)`).
   Convert into the common `Violation` model; keep tool-specific data in `raw`. Use the hardened
   `Xml` helper for XML (no DTDs, no external entities).
2. Register it in `Readers`.
3. Add a real report as a fixture and tests covering: normal results, a result without a line,
   Windows paths, an empty report.
4. Mention the analyzer in the README table.

## Pull requests

- Open an issue first for anything larger than a small fix, so we agree on the approach.
- `mvn verify` must pass.
- Update `CHANGELOG.md` under *Unreleased* if behavior changes.
- Write commit messages in the imperative: "Match moved files by context hash".
- By submitting a pull request you agree that your contribution is licensed under the
  [Apache License 2.0](LICENSE) (section 5 of the license).

## Good first issues

- Capture real PMD and SpotBugs reports from a small public project and add them as test fixtures
- Add a reproducible benchmark script (clone repo, run analyzer at two commits, compare)
- Make the baseline file smaller (see [docs/BENCHMARK.md](docs/BENCHMARK.md))
- Add an option to disable or restrict tier-3 matching
- Add a reader for another SARIF-producing analyzer and test it against real output

## Reporting bugs and security issues

Use the issue templates. For security problems follow [SECURITY.md](SECURITY.md) and do not open
a public issue.

## Code of Conduct

This project follows the [Contributor Covenant](CODE_OF_CONDUCT.md). Be kind and assume good intent.
